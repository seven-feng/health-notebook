# 拍照报告日期缺失与趋势缺失复现

> **专题历史记录。** 下文结果与安装模式只对应各段记录的时间，不代表当前手机状态或全部功能验收。最新汇总见[当前状态与待办](当前状态与待办.md)，日常运行见[本地开发与测试](本地开发与测试.md)。

2026-10-23。最初使用用户手机中的原件复现日期和趋势问题；下文先保留复现结果，修复进展见末尾。

## 复现方式

通过 devicectl 只读复制 App Documents 中的三份 PDF。为避免与另一项报告增强工作互相影响，把当前解析器、领域逻辑和 Swift 提取器冻结到 `tmp/photo-date-repro/`。

使用实际 `LocalPdfExtractor` 源码在 macOS PDFKit/Vision 上重跑，再调用冻结的 `parsePages` 和 `buildSeries`。原件及完整提取结果只放在忽略提交的 `private-fixtures/photo-date-20261023/`，这里不保存姓名、身份号码或检验数值。

这是从真机原件开始的本地流水线复现；未读取手机加密数据库，也未证明手机已保存的每个字段与这次 macOS OCR 逐字一致。确认状态仅在内存中模拟。

## 结果

| 原件 | 提取指标数 | 自动提取日期 | 模板 | 模拟确认后进入趋势的指标数 |
| --- | ---: | --- | --- | ---: |
| 较早导入的完整报告 | 23 | 有 | 浙一双列表格 | 23 |
| 新拍照报告 A | 23 | 无 | 浙一双列表格 | 0 |
| 新拍照报告 B | 22 | 无 | 浙一单列表格 | 0 |

两份拍照原件都保留了右上方页眉日期，但没有拍到底部采集时间。OCR 成功读出了页眉日期；当前浙一解析器只从“采集时间 / 采样时间”取日期，所以都输出空字符串。

`buildSeries` 会排除日期为空的报告。三份一起传入时，得到 23 个序列，每个只有一个点；指标页仅在点数大于 1 时显示趋势图。这与用户描述一致。

内存中补入原件页眉日期并模拟完成指标核对后，有 16 个序列跨两个日期。此实验用于区分日期缺失与其他原因，不代表可以自动把所有页眉日期认定为采样日期。

另有独立问题：拍照报告 B 中 5 项因为单位识别错误或串行，未建立指标代码，因此补日期不能让所有项目都进入趋势。报告 A 与较早完整报告对应同一次检查，也不应当被解释为一次新的检查。

## 修正边界

1. 保留明确的采样日期优先级；缺失时识别经过模板位置验证的页眉日期，并在核对时明确来源，不能伪称为采样日期。来源不清楚或冲突时由用户确认。
2. 指标页应解释有多少份报告因缺日期而暂未计入，并提供补录入口，避免只显示“目前只有一次检查结果”。
3. 已导入记录需要独立考虑补录或重新提取；仅修复新导入逻辑不会自动修好现存记录，也不能覆盖用户核对过的字段。
4. 保留单位、样本和指标映射校验；修复 OCR 的单位错位后再比较，不通过放宽匹配强行连线。

## 日期修复已实现

根据用户确认的规则：优先读取明确的采集／采样时间或日期；没有标注时，使用经过验证的浙一报告版式中、表格上方右侧独立的页眉日期作为检查日期。页眉来源单独保存为 `dateSource: header`，界面显示“日期来源：报告页眉”，不增加额外的确认步骤。明确写了“报告日期”的则保留其来源。

非法日期、多个互相冲突的日期、出生日期、打印日期、编号和表格中的数字不会被当成检查日期。有明确采样日期但无法读清时，也不会用其他日期强行替换。

旧报告在启动时进行一次补齐：仅处理已知浙一模板、日期为空且原件可读取的记录。原件提取成功后记录已尝试状态，后续打开不反复 OCR；原件暂时受锁定保护时允许下次重试。数据库在写入时重新比较当前元数据，已编辑或删除的记录不会被覆盖。仅更新日期和相应的缺失提示，原指标、确认状态、成员、就诊关联和人工修改均保留，并记录修改前的版本。

指标页新增缺日期提示与补录入口。此次没有放宽指标匹配规则，也没有处理那份照片中的单位错位问题。
