# 微信“其他应用打开”PDF 接收修复

> **专题历史记录。** 下文结果与安装模式只对应各段记录的时间，不代表当前手机状态或全部功能验收。最新汇总见[当前状态与待办](当前状态与待办.md)，日常运行见[本地开发与测试](本地开发与测试.md)。

日期：2026-10-23

## 现场证据

用户反馈 iPhone 能进入 App，但没有报告。只读检查设备发现：iOS 的 `Documents/Inbox` 留有 7 个 PDF（其中有重复副本），应用自己的 `Application Support/incoming` 为空。旧接收代码只枚举后者；首次启动缺少 launchOptions URL 接收，热启动则仅依赖 AppState/React Native Linking 触发扫描。文件准备完成后没有独立通知。

## 修改

- 新增 `IncomingPdfInbox`，统一枚举系统收件箱与应用收件箱。App 启动时可补收未处理文件。
- 处理冷启动 URL，并在接收完成后发送 `onIncomingFile`。页面先订阅再扫描，避免错过启动期间的文件。
- 外部文件使用安全作用域和 NSFileCoordinator 读取，暂存完成后原子改名；应用收件箱中的文件无需再次复制。
- 接收失败保留不含文件名和病情内容的提示，启动后可显示，不再静默丢失错误。
- 保持按档案和文件哈希去重；原件持久化成功后才清理收件副本。删除限定两个收件目录，拒绝符号链接和目录。
- 导入时显示“正在导入报告…”，完成后打开单份报告或整份文档。导入期间切换档案不会跳到另一档案的报告。
- 无新增依赖，不改变 OCR 解析逻辑、确认状态或云端行为。

## 验证

- iOS 原生收件箱测试 6 项通过：无 URL 回调的启动恢复、通知顺序、重复投递、安全删除、失败恢复、20 MB 限制。
- TypeScript、lint、原有自动化测试通过；新增页面事件和导入去重测试通过。
- 模拟器另建临时发送 App，使用 `UIDocumentInteractionController` 的“其他应用打开”发送合成 PDF，验证真实系统交接路径，而非直接往应用收件目录放文件。
- Release 已构建并覆盖安装到用户连接的 iPhone。原有应用数据保留。
- 真机最初因锁屏无法启动；用户解锁并按“打开 App、再从微信打开 PDF”的步骤复测，已确认“已经看到导入的报告”。
- 模拟器后台分享交接通过；冷启动收件恢复由 6 项原生测试中的专门用例覆盖。Debug 冷启动会进入开发启动页，不能用它代替 Release 冷启动验证。模拟器 Release 也已编译通过；未把 Debug 的启动页误记为 Release 冷启动通过。
