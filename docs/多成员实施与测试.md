## 操作方式

- 2026-10-27 设置整理后：打开 App 默认进入“我”，在记录、指标页右上角切换成员，当前标签页保持不变。设置页改为全局入口，不提供成员切换。
- 点成员按钮 → 添加家庭成员；称呼必填，姓名和出生日期可选。设置 → 家庭成员 → 选择成员，可编辑任意成员资料；这里也可添加成员，保存后回到管理列表，不改变记录页当前人。详见[设置页整理](设置页整理-2026-10-27.md)。
- 当前成员的报告、待核对项、原件、就诊及指标独立显示。旧数据自动保留在“我”，不删除或重新识别原件。
- PDF、相册、相机以及外部接收归入接收时选定的成员。姓名不同会提示确认，不自动换人；重试、恢复、重新识别和手动归档使用原件已保存的成员 ID。
- 常规详情、原报告片段、手势查看、紧凑指标、分组核对和编辑沿用原实现。报告姓名缺失仍需在确认时补充；明确确认的姓名差异不拆散同一成员的指标历史。

当前支持新增和编辑成员。成员是本机资料分类，本轮未增加账号、云同步、成员删除或已归档报告跨成员移动。

## 数据升级

`src/db/migrations.ts` 在事务内升级到 SQLite `user_version = 3`，新增 members，给 documents / reports / visits 的 JSON 写入 memberId 及相应索引。旧患者资料名称迁入“我”的成员资料。指标、来源坐标、修订历史和就诊关联保留。

同一个原始文件按 `[memberId, hash]` 去重，不同成员使用不同原件 ID 与私有文件副本。数据库写入层校验成员存在、原件归属、报告归属、姓名冲突确认和就诊关联，避免仅依靠页面过滤。

RecordsProvider 对三个标签页统一过滤，刷新有过期请求保护；外部接收任务在排队前捕获文件列表及当前成员，并为待清理的接收副本保留归属绑定。

## 就诊隔离补充（2026-10-25 文档复核）

当前源码中，`RecordsProvider` 按 `activeId` 同时过滤报告、原件和就诊，首页数量也分别计算；就诊详情只在当前成员集合查找记录。数据库继续拒绝跨成员原件及关联检验。切换成员后应只看到该成员的记录。

`tests/components/visit-members.test.tsx` 已覆盖用真实成员选择器切换至有记录／无记录成员，检查就诊列表、数量和重新读取后的隔离。该用例包含在 2026-10-24 的 33 套／339 项完整检查中，见 `tmp/visit-exam-format/verify.log`；本次仅核查源码与日志，未重跑或新增设备验收。

同一病历分别导入两个成员会保留独立记录与原件副本。因此内容相同本身不能证明列表泄漏；排查时应核对当前成员与记录的 `memberId`，不能按正文相同自动删除或改归属。当前仍没有跨成员移动已归档资料的产品入口。
