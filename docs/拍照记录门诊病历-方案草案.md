# 拍照记录门诊病历：方案草案

> **历史方案与样本试验。2026-10-23 已按审批原型接入首版代码。** 本文保留当时的试验描述，实施范围与验证见[病历实施记录](门诊病历实施记录.md)，最新进度见[当前状态与待办](当前状态与待办.md)。

2026-10-23。需求：拍摄纸质门诊病历，自动生成可核对、修改和保存的就诊记录，沿用当前成员和就诊时间线。

## 本次样本验证

用户提供一张倒置的、略有倾斜的纸质门诊病历照片。分别用原图和旋转 180° 后的图，在 Mac 上编译运行当前 `PdfExtractor.swift`，通过 PDFKit/Vision 本地提取。测试图片以与现有图片流程相同的最长边 800 点包装为单页 PDF；这属于本地引擎试验，不等同于完整的 iPhone／Android 拍照导入验收。

两种方向都能在原生 OCR 返回的阅读顺序中找到门诊病历、就诊时间、就诊科室、主诉、现病史、既往史、体格检查、诊断、处理这 9 个标题；明确标注的就诊日期也被读到。按标题切分，能得到 6 段非空正文候选。原图与旋转图分别提取 467／466 字，这不是逐字准确率结论。

当前产品的解析器两次都输出 `template: null`、0 项指标、空日期。原因是它只生成检验表格结果，没有把叙述病历转换为 Visit 的逻辑。此外，现有按字符坐标拼表格行的逻辑，会把这类带倾斜、较长段落的文字顺序打散；不能将它直接复用于病历正文。

结论：这个样本不需要先引入 LLM。已有本地 OCR 可以提供文字，主要要新增病历结构整理、原文溯源和就诊记录保存流程。方向矫正与裁剪应继续完善，但不能只修旋转而不增加病历解析。

真实照片、原生输出和文字只保存在忽略目录 `private-fixtures/visit-note-20261023/`。不复制身份信息或具体病情到此文档。测试程序与不含正文的统计在 `tmp/visit-note-repro/`。

## 建议的体验

1. 用户仍可从首页拍照或选择照片。识别到“门诊病历”及明确正文标题时，直接进入“核对就诊记录”；检验表格继续使用现有核对流程。无法确定类型时再让用户选择用途，也允许更正分类。
2. 顶部显示就诊日期、医院、科室。记录归属默认沿用当前成员，患者姓名不匹配时沿用档案核对规则。必须区分出生日期、就诊时间和打印时间。
3. 主要显示“就诊原因（主诉）”“医生诊断（原文）”“处理／医嘱（原文）”。现病史、既往史、体格检查放在“更多病历内容”中展开，避免初次看到长表单。
4. 字段可编辑；点原文即可看到对应照片区域，放大交互沿用已有组件。没有识别到的字段留空，不生成诊断、处方或复诊日期。
5. 保存为一次就诊，出现在当前成员的时间线，关联这张病历原件。之后可关联既有检验报告。没有检验报告，也可以独立保存就诊记录。
6. OCR 不确定或版式不支持时，保留整页原件与全文供手动整理，不再以“未提取到检验指标”结束病历流程。

## 第一版实现边界

- 覆盖有明确标题的打印门诊病历；从当前样本开始，加不同医院版式和匿名合成样本验证。
- 保留 OCR 的原始行／块关系与坐标，处理倾斜和阅读顺序；不要为了叙述病历修改已经验证过的检验表格拼行规则。iOS 与 Android 分别保留其原生行结构。
- 用“主诉、现病史、既往史、体格检查、诊断、处理／处置／医嘱”等标签划分段落；正文逐段保留原文。暂不把无明确标题的内容自动总结成新的医学字段。
- 诊断仅作为原文记录，不作为系统判断。用药和复诊信息第一版保留在处理／医嘱正文；不猜药名、剂量、频率，不把相对复诊时间直接转换为日历提醒。
- 体格检查中的数字第一版保留在原文，不自动混入检验指标趋势。
- 先支持一张照片对应一份病历；多张照片合并同一次就诊随后增加，避免按日期自动合并不同就诊。
- 保持本地处理与本地保存，第一版无需外部 API 或 LLM。

## 数据与验收

在现有 Visit 的日期、标题、备注、成员和关联检验报告之上，增加医院、科室、原文分段、原始 OCR 文本及原件／位置引用。原件需能直接属于就诊，不能要求先伪造一个检验 Report。用户编辑值与 OCR 原文分别保存；读取历史记录不重复 OCR。

删除就诊、原件和检验报告时检查各自的关联，不能连带删除还被其他记录引用的原件。重新识别先产生候选，不能覆盖已修改字段。

最低验收覆盖：原图与旋转图、倾斜、模糊、正文换行、缺字段、多个日期、多个诊断段落、文字结果、患者与当前成员不符、取消／保存／重启恢复、删除关联原件、重新识别保留人工修改。两端本地验证后再安装到真机；不能以一个样本识别到标题就宣称所有病历准确。
