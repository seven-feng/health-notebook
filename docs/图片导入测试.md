# 拍照与相册导入

> **专题历史记录。** 下文结果与安装模式只对应各段记录的时间，不代表当前手机状态或全部功能验收。最新汇总见[当前状态与待办](当前状态与待办.md)，日常运行见[本地开发与测试](本地开发与测试.md)。

在“记录”页选择“拍照识别”或“从相册选择”，一次一张。拖动裁剪框四角，或拖动框内区域；可旋转、恢复裁剪或重新选择。点“开始识别”后，按现有核对流程保存。照片识别后统一确认保存；只有具体疑点需要单独核对。日期缺失时请对照原图补充。

图片和识别都在本机处理，不调用云端 OCR 或 LLM。相册原图不变，App 保存确认裁剪后的报告，导出格式为 PDF。未知版式仍可保留原件、手动整理。当前没有批量选图、透视校正或模糊检测。

## 本机运行

本次新增原生依赖，需要安装新版开发包。本机两个模拟器已经更新，Metro 仍使用 8081 端口。其他设备更新时分别运行：

```bash
cd /Users/fanqie/Documents/doctor
nvm use
npm ci
npm run ios
npm run android
```

已安装新版包后，日常只需 `npm start`，在同一个开发服务终端按 `i` 或 `a` 打开 App。已有开发服务运行时不要再开第二个。

iOS 模拟器无法实拍，可以把合成图片放进模拟器相册测试。Android 模拟器的相机是虚拟场景，可以验证拍摄回调，不能代表真实纸质报告的 OCR 效果。

## 合成图片与两端流程

只在专用测试模拟器运行；图库需以刚加入的合成报告为第一张，脚本会选择第一张图片并暂存未确认记录。不会确认患者信息或写入正式指标趋势。不对含真实资料的图库运行此脚本。

生成图片需要本机已安装的 Poppler：

```bash
mkdir -p tmp
pdftoppm -scale-to 2600 -png -singlefile assets/samples/sample-first.pdf tmp/photo-sample
xcrun simctl addmedia booted tmp/photo-sample.png
~/Library/Android/sdk/platform-tools/adb -s emulator-5554 push tmp/photo-sample.png /sdcard/Pictures/doctor-photo-sample.png
~/Library/Android/sdk/platform-tools/adb -s emulator-5554 shell am broadcast -a android.intent.action.MEDIA_SCANNER_SCAN_FILE -d file:///sdcard/Pictures/doctor-photo-sample.png
```

保持 Metro 和已安装新版 App 的模拟器运行：

```bash
npm run e2e:ios -- .maestro/photo-import.yaml
npm run e2e:android -- .maestro/photo-import.yaml
```

脚本验证系统选图、拖动裁剪、恢复裁剪、旋转、识别、原图和行图查看、暂存返回。选择器定位针对当前 iPhone 16 Pro / iOS 18.6（中文）和 Pixel 3a / API 34（英文），其他系统版本需调整选择器定位。已导入相同图片时打开原记录。截图在 `test-results/`；这里只验证交互链路，不把流程通过当作所有字段识别正确。

## 原生转换和 OCR

新增合成测试 `tests/native/PhotoDocumentTests.swift` 与 Android `PhotoDocumentTest.kt`：把合成 PDF 渲染成位图，再调用 App 实际图片转换器生成无文字层 PDF，使用实际本地 OCR 检查核心文本，同时检查损坏图片被拒绝。每端 2 项测试，无需真实病历。

```bash
GEM_HOME=/opt/homebrew/Cellar/cocoapods/1.16.2_1/libexec /opt/homebrew/opt/ruby/bin/ruby scripts/prepare-ios-ocr-tests.rb
xcodebuild test -project tmp/ocr/ios-tests/LocalOCRTests.xcodeproj -scheme LocalOCRTests -destination 'platform=iOS Simulator,name=iPhone 16 Pro' -derivedDataPath .local/photo-tests -only-testing:LocalOCRTests/PhotoDocumentTests CODE_SIGN_IDENTITY=-
```

Android 在 `android/` 目录执行：

```bash
JAVA_HOME=/opt/homebrew/opt/openjdk@17/libexec/openjdk.jdk/Contents/Home ./gradlew :local-pdf:connectedDebugAndroidTest -PreactNativeArchitectures=arm64-v8a -Pandroid.testInstrumentationRunnerArguments.class=expo.modules.localpdf.PhotoDocumentTest
```

普通代码检查为 `npm run verify`，发布 JS 包检查为 `npm run check:bundles`。

## 已知效果与真机检查

本次相册导入同一张合成报告：iOS 提取 3 项，Android 提取 2 项；Android 一项单位误读未能整理，日期也未被正确提取。界面保留缺项／日期提示，要求核对。这说明图片入口和本地 OCR 已接通，不代表任意照片、医院或版式都能完整识别。既有 PDF 样本的匹配结果不能套用到实拍照片。

后续在 iPhone 和 Android 真机检查：相机权限允许／拒绝后恢复、拍摄与取消、横竖方向和 HEIC、整页裁剪、反光或倾斜、较大图片的耗时和内存、离线 Release，以及逐项对照真实报告的名称、数值、单位、日期和参考范围。拍摄时尽量正对报告、光线均匀，保留姓名、日期和完整表格。

## 裁切截图识别修复 · 2026-10-23

- 用户提供的浙一双栏血常规截图可读出文字，但原规则要求表头位于页面顶部 20%，并只读取页面前 90% 的指标。裁掉底部空白后，表头和末行的位置比例变化，导致整页被判为不支持或漏掉末行。
- 对短于标准报告的图片，按页面宽度归一化纵向模板坐标；解析结束后将指标、原图裁剪及补读区域还原到输入图片坐标。仍校验医院、检验类型和左右表格列，未新增通用医院模板。仅 OCR 输出兼容这次实际遇到的医院名“大／犬”误读，不对 PDF 文字层放宽此规则。
- iOS 与 Android 模拟器调用实际图片整理步骤（缩放、全图裁剪、JPEG 保存）、图片转 PDF、本地 OCR 和字段解析，两端均从 0 项恢复为 23 项，23 个数值逐项与用户图片一致。该次耗时约 2.1 秒／3.9 秒，含图片处理，仅代表这次模拟器测量。部分名称、单位和箭头仍不准确，保留核对提示；没有采样日期就保持缺失。
- 同时测试另一张倾斜、上部被遮挡的体检照片及裁掉背景版本。两端都读出了部分文字，但该多段表格尚未适配，均未生成指标；裁剪不能解决版式整理和倾斜造成的错行。没有将这张照片标为已支持。
- `npm run verify` 通过：137 个 Jest 用例、类型检查、lint 和 HTTP 测试。原两份 PDF 在两端既有 OCR 输出上的 45 项字段回归全部匹配。证据保留在私有目录 `tmp/photo-diagnosis-20261023/`，原图和含个人资料的 OCR 内容不加入公开测试样本。新增回归测试使用合成数据，覆盖裁切后末行、原件坐标、局部补读、医院名容错边界。
- 测试未写入或确认病历，只使用模拟器缓存；测试后清理缓存。代码仅涉及 TypeScript 解析，无需新增原生依赖；Release 真机需重新打包安装，已导入的记录再点“重新识别原报告”。
